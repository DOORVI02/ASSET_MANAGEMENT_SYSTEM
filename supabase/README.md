# Supabase foundation

Phase 8 scaffolding only — no business schema, no deployed functions, no connection to a
live project has been established from this repository. See `.agents/phases.md` Phase 8
for status and `.agents/plan.md` sections 11–15 for the architecture and security rules
this must follow.

## Layout

- `config.toml` — local stack configuration, generated by `supabase init`. Untouched
  defaults; nothing here has been customized yet.
- `migrations/` — empty. Phase 9 adds versioned schema migrations here.
- `functions/_shared/` — Edge Function helpers (`cors.ts`, `errors.ts`, `request-id.ts`,
  `auth.ts`, `validation.ts`). Foundation-phase skeletons: `auth.ts`'s profile lookup is
  a stub until the `profiles` table exists (Phase 9), and none of these have been
  exercised against a running function — this environment has no Docker, and
  `supabase functions serve` requires it.

## Commands

Run from the repository root (not `frontend/`) with `npx supabase <command>` — no
global install is required or assumed.

| Command                                              | What it does                                                                                    | Verified here?                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| `npx supabase init`                                    | Scaffold `config.toml`. Already run.                                                              | Yes.                                                    |
| `npx supabase start`                                   | Start the full local stack (Postgres, Auth, Storage, Studio) in Docker.                           | **No — Docker is not available in this environment.** |
| `npx supabase stop`                                    | Stop the local stack.                                                                              | No, same reason.                                       |
| `npx supabase db reset`                                | Drop and rebuild the local database from `migrations/` + `seed.sql`.                               | No, same reason.                                       |
| `npx supabase link --project-ref <ref>`                | Associate this folder with a hosted project. Prompts for/uses an access token from `supabase login`. | Not run — needs a decision on which project and an interactive login. |
| `npx supabase gen types typescript --local`            | Regenerate `frontend/src/lib/database.types.ts` from the local stack.                            | No, needs `start` first.                               |
| `npx supabase gen types typescript --linked`           | Same, from the linked hosted project.                                                              | No, needs `link` first.                                |
| `npx supabase functions serve`                         | Run Edge Functions locally.                                                                        | No — also needs Docker.                                |
| `npx supabase secrets set --env-file .env`             | Push Edge Function secrets to a linked hosted project.                                             | Not run.                                                |

## What is genuinely done vs. deferred

Done, network-free, reversible: `config.toml` scaffold, this folder layout, the shared
function helper skeletons, `frontend/src/lib/supabase.ts` + `env.ts` (the one browser
client, URL/publishable-key only), `frontend/src/lib/database.types.ts` (a typed empty
placeholder — see its own doc comment), and `.env.example` at the repo root.

Deliberately not done without a separate, explicit decision: linking this folder to any
hosted Supabase project, running any command that authenticates over the network,
generating real database types, or setting Edge Function secrets. `supabase.txt` and
`cloudinary.txt` contain what looks like one already-provisioned hosted project's
credentials; using them to actively connect and start issuing schema/data commands
against a live project is exactly the kind of hard-to-reverse, shared-system action this
project's working rules ask to confirm before taking, not just before starting the phase
in general.
